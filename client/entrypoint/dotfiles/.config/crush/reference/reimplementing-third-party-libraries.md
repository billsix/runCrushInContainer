## The default is to USE libraries — this is the exception

**Most of the time, depend on the library; don't rewrite it.** Reimplementing is a cost (you now own it,
including the bugs) and this doc is for the minority of cases where that cost is worth paying. It is NOT a
licence to reinvent wheels. Reach for it only when a concrete reason below holds, and say which one.

**Good reasons to reimplement/adapt in-tree:**

- **You want a *tailored* version** — the upstream does far more than you need, and a small, readable,
  purpose-built version you fully understand is worth more than the general one (the teaching-codebase
  case especially: the code is meant to be *read*).
- **You want to avoid dependency / framework hell** — a library whose real cost is its *transitive*
  dependency tree (the JS/npm ecosystem is the archetype). Pulling one widget should not pull a hundred
  packages and an install-script attack surface. Reimplementing the one widget you want, in the platform's
  vanilla language, keeps the tree flat and the surface zero.
- **You want it to run on your own substrate** — the upstream targets a backend you're replacing (e.g.
  `pgzero_gl`, in **github.com/billsix/modelviewprojection**, reimplements the PyGame Zero API on GLFW +
  OpenGL so the original game logic runs unmodified on modern GL).
- **Long-term self-containment** — one owned file won't rot, get yanked, or change under you the way a
  pinned external dep can.

**Do NOT reimplement when:** the library is large/subtle and correctness-critical (crypto, parsers,
codecs, numerics) — depend on the vetted one; a thin wrapper would do; or the licence forbids it. When
unsure whether it's worth it, say so and ask.

## The crux: which mode you're in decides the licence — and it's not optional

There are **two** ways to do this, and they have **different legal consequences**. State which one in the
file header; don't blur them.

1. **Clean-room reimplementation** — you reimplement the library's *API / behaviour* **without copying its
   source** (you read docs/tests, or a spec, and write fresh code). The result is **your** work; you may
   licence it however you like. **`pgzero_gl` (in github.com/billsix/modelviewprojection) is this case** —
   and it still chose to match the upstream licence (LGPL-2.1) as courtesy and safety. Matching is a
   *choice* here, strongly recommended.

2. **Source adaptation (a derivative work)** — you **start from the upstream source** and rewrite/trim it
   (the "pull down the source and rewrite it in vanilla JS, removing the unnecessary parts" case). The
   result is a **derivative work**: you **MUST** keep it under the upstream licence (or a compatible one
   the upstream licence permits) and comply with that licence's terms (retain copyright notices, carry the
   licence text, state your changes). **You cannot relicense it to something more permissive.** Matching is
   an *obligation* here, not a choice.

**Be honest about which you did.** If any upstream source made it into your file, you are in case 2 — treat
it as a derivative. Only genuinely-fresh code from behaviour/spec is case 1. When in doubt, assume case 2
(the stricter path) and match the upstream licence. **This is not legal advice** — for a licence you don't
recognise, or a copyleft/commercial boundary, surface it and ask before shipping.

## The mechanics — the `pgzero_gl` pattern (do it exactly like this)

Every reimplemented/adapted file carries a header, and the package carries the upstream licence text.

**Per-file header** (comment syntax per language — `#`, `//`, …):

```python
# Copyright (c) <year> <You: full name>
# SPDX-License-Identifier: <UPSTREAM-licence>        # e.g. LGPL-2.1-only — the upstream's, matched
# Generated by Claude (Anthropic); a clean-room reimplementation of the <upstream> APIs,
#   under the same license as <upstream> (<licence long name>).         # or: "an adaptation of <upstream> source"
# Full license text: <repo-relative path to the vendored LICENSE>
# License source: <upstream raw licence URL>
```

- **`Copyright` is yours**, with the year; **`SPDX-License-Identifier` is the *upstream's* licence** (SPDX
  id — https://spdx.org/licenses/), matched. Use a real SPDX id, not prose.
- **State the mode in plain words** on the "reimplementation" line — "clean-room reimplementation of the X
  APIs" (case 1) vs "an adaptation of X's source" (case 2) — and name the upstream.
- **`Generated by Claude (Anthropic)`** where that's true — the attribution convention for an
  AI-authored reimplementation (keep the human `Copyright` line regardless).
- **Point at the vendored licence file and the upstream licence URL**, so a reader can verify provenance.

**A module/file docstring (or top comment) that credits the original** — authors, project, book/repo, and
**links to the upstream source** — so the lineage is discoverable from the code, e.g. `pgzero_gl/__init__.py`:
names Andrew Gillett et al., Raspberry Pi Press, and links
`https://github.com/raspberrypipress/Code-the-Classics-Vol1` and the book page.

**A vendored `LICENSE` file beside the code** (the package dir), containing the upstream licence text,
referenced by the header's "Full license text" path.

## The discipline: tailored, trimmed, in its own file

- **Its own file (or small package)** — don't scatter the reimplementation through your app; keep it
  isolated behind the same surface you'd have imported, so swapping back to the real library (or forward
  to a better reimplementation) is a one-line change.
- **Trim to what you use** — the point is a small version you fully understand. Drop the upstream's
  features you don't need; say so. Reproduce the behaviour you *do* keep exactly (so callers don't notice).
- **Vanilla / platform-native as far as possible** — the whole value in the dependency-hell case is that
  the result has *no* runtime dependency. In JS that means vanilla DOM + the house JSDoc-typed style
  (`~/.claude/reference/javascript-coding-standard.md`), not a framework.

## Fetching the source to learn from is transient — it is NOT a dependency

To learn from (or adapt) the upstream you may pull its source — `git clone`, a release tarball, or a
package manager used **only to download source**: `npm pack <pkg>` / `deno` / `pip download --no-deps`.
That checkout is a *reference*, not a dependency: it does **not** enter your lockfile, image, or runtime.
Delete it (or keep it under a throwaway path) once the reimplementation is written. The shipped artifact is
your one owned file + its vendored `LICENSE`; nothing external is pinned. (In an ephemeral build image the
fetch is doubly safe — it can't persist — but still keep it out of the committed tree.)

## Not the same as re-vendoring source as-is

This doc is the **reimplement/adapt** path. Its sibling,
`~/.claude/reference/vendoring-third-party-source-deps.md`, is the **import-as-is** path: vendor the
upstream source *unchanged* and re-sync it on a bump via `update_dep_common.sh`. Use that one when you want
the real library's code tracked in-tree but not rewritten (you keep upstream's licence file and headers
verbatim there too). This doc is for when you deliberately write your *own* version instead.

## Worked example — `pgzero_gl` (modelviewprojection)

github.com/billsix/modelviewprojection reimplemented the **PyGame Zero / pygame** API as
`src/modelviewprojection/pgzero_gl/` — a clean-room shim on GLFW + OpenGL 3.3 core, so the original "Code
the Classics" game logic runs unmodified on modern GL. Case 1 (clean-room), matched to pygame's
**LGPL-2.1-only** by choice. Each module carries the header above (copyright the maintainer, SPDX
`LGPL-2.1-only`, "clean-room reimplementation … under the same license as pygame", vendored
`pgzero_gl/LICENSE`, upstream LGPL URL) and a docstring crediting the original authors + linking the
upstream repo and book. The result: no `pygame`/`pgzero` runtime dependency, a small readable rendering
layer the project owns, and a clear, honest licence story.
